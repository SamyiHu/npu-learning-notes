# 第 2 课：CPU / GPU / NPU——为什么要有专用硬件

> 学习日期：2026-08-17（讲义编写日，自学后待讨论）
> 阶段：02-为何需要NPU
> 前提：第 1 课（量化）；体系结构基础（流水线、SIMD、cache 你都懂，本课只做"NPU 视角"的串联）
> 方式：讲义 + 手算。算力账要自己算一遍才有感觉

---

## 一、核心一句话

**CPU 为"什么都会"优化，GPU 为"一大堆同样的线程"优化，NPU 为"矩阵乘法这条流水线"优化——把不需要的东西全扔掉，剩下的就快、就省电。**
专用化（domain-specific）是这十年体系结构的主旋律，NPU 是其中最成功的案例之一。

---

## 二、先定义"算力"：TOPS

```
1 TOPS = 每秒 1 万亿次（10¹²）运算
惯例：1 次乘法 + 1 次加法 = 2 次运算，即 1 MAC = 2 ops
```

所以"RK3588 NPU 6 TOPS"表示三核合起来峰值约每秒 6 万亿次运算；按 1 MAC = 2 ops 折算，约每秒 3 万亿次 MAC（30000 亿 MAC/s）。记住 1 MAC = 2 ops，后面算账都用它。

---

## 三、手算：一层卷积在三种处理器上各要多久

拿一个真实的层做例子（第一个学过的：VGG16 第一层卷积，3×3 / stride 1 / pad 1，224→224）：

```
输入 224×224×3，64 个 3×3×3 卷积核，输出 224×224×64

MAC 数 = 输出位置 × 核数 × 每核乘加数
       = (224×224) × 64 × (3×3×3)
       = 50176 × 64 × 27
       ≈ 0.87 亿 MAC = 1.73 亿 ops ≈ 0.17 GOP
```

### CPU 账（以 A55 @2GHz 为例，就是你板子上的小核）

A55 有 128-bit NEON，INT8 点积一条指令吃 16 个数。理论峰值约每周期 16~32 MAC（双发射 SIMD 才吃满），**取乐观值 32**：

```
峰值 = 32 MAC/cycle × 2 GHz = 64 GMAC/s = 0.128 TOPS
理论时间 = 0.87 亿 MAC ÷ 640 亿 MAC/s ≈ 1.4 ms
```

但实际还要打 3~10 倍折扣，因为 CPU 同时在干别的：取指译码、cache miss 等内存、函数调用、操作系统调度……**实际 5~15 ms**。一个 ResNet 有 50+ 个层，图大一点的模型 CPU 跑一帧就是几百 ms 到几秒——视频每帧只有 33ms 预算，CPU 不可能完成。

### NPU 账（RK3588 单核 2 TOPS）

```
理论时间 = 0.17 GOP ÷ 2 TOPS = 87 µs
考虑利用率 30~60%（下阶段讲为什么不是 100%）≈ 0.15~0.3 ms
```

**同一个层，NPU 单核实际比 CPU 快约 20~100 倍**（理论 1.4 ms vs 87 µs ≈ 16×；CPU 实际要打 3~10 折，NPU 也要算利用率），而且三核并行、功耗只有几瓦。

### 这笔账的验证意义

你现在做的性能分析（峰值 vs 实际、利用率折扣）和 IC 里做 benchmark 分析是同一件事。NPU 的"利用率"就是它的"效率指标"，阶段三会看到真实模型占用率怎么查（`/sys/kernel/debug/rknpu/load`）。

## 四、三种处理器的根本差异

| | CPU（A76/A55） | GPU（Mali） | NPU（RKNPU） |
|---|---|---|---|
| 设计目标 | 通用，任何程序 | 大量同构线程（图形出身） | 矩阵乘法+少量固定算子 |
| 并行方式 | 少核深流水 + SIMD | 上百核 SIMT | **MAC 阵列**（上千乘法器一拍齐上） |
| 控制开销 | 取指/译码/分支预测/乱序，一样不少 | 有，但摊到多线程 | **几乎没有指令流**，任务级驱动 |
| 数据通路 | 通用寄存器堆 | 大寄存器文件 + 共享存储 | 权重/激活专用缓冲，搬运由 DMA 包办 |
| 精度 | FP32/FP16/INT8 | FP 为主 | **INT8/INT16 为主**（3576/3588 加 FP16） |
| 一帧图像推理 | 数百 ms~秒级 | 数十 ms，功耗高 | **几 ms~几十 ms，几瓦** |
| 代价 | — | — | **只会算神经网络这一件事**，别的都要 CPU 伺候 |

### CPU 慢在哪（逐条对上你的体系结构知识）

1. **指令开销**：每个 MAC 都要取指、译码。NEON 一条指令 16 个 MAC 已经是在"摊薄"指令开销，但循环控制、地址计算仍占周期
2. **寄存器不够**：卷积要同时握着一核权重（9 个）+ 一行输入 + 累加器，通用寄存器堆捉襟见肘，只能反复访存
3. **cache 不是为它设计的**：权重/激活的访问模式（滑动窗口、多通道）局部性特殊，通用 cache 替代不了**专门排布的片上缓冲**
4. **单核就那么多**：8 核全开也就 ~1 TOPS 量级的 INT8 峰值，还和系统任务抢核

### GPU 快了为什么还要 NPU

- GPU 的并行是"线程级"，天然浮点导向；做 INT8 量化推理时大量面积花在它不擅长的调度上
- GPU 功耗高（几十瓦级）：Mali 在手机/嵌入式 SoC 里规模小（RK3588 的 G610 也只有 4 核），做推理不如同面积 NPU 划算
- **NPU 干脆不做通用计算**：没有分支预测、没有乱序、没有复杂中断——硅片面积全铺 MAC 阵列和搬运通路。RK3588 每核一拍 1024 个 INT8 MAC（下阶段拆解），这就是"专用"两个字换成的东西

---

## 五、NPU 的低功耗从哪来（端侧的命门）

1. **INT8**：第 1 课讲过，乘法器小 ~9 倍，数据搬运少 4 倍
2. **无指令流开销**：不取指不译码，控制功耗趋零；驱动数据流而非指令流
3. **深流水 + 规整**：数据通路极度规则，时钟好做、电压好压
4. **专用搬运**：DMA + 片上缓冲让数据"少跑路、不绕路"（阶段三主题）

第三方实测 RK3588：NPU 满载时整机功耗只多 2~3 W，按 6 TOPS 峰值折算约 **2~3 TOPS/W**（按有效吞吐则约 1 TOPS/W 量级；官方未公布该数据，只作量级参考）。同等算力用 CPU 跑，功耗是它的几十倍。

## 六、"NPU 不包打天下"——它在系统里的真实位置

这个认知比算力数字重要：

```
摄像头/图片 → [CPU 或 RGA: 缩放/色转] → [NPU: 卷积/全连接等主力层] → [CPU: 后处理/业务逻辑]
```

- **预处理**（resize、颜色空间转换）→ RGA 硬件（阶段四见）
- **主力网络层** → NPU
- **不支持的算子、NMS、画框、决策** → CPU（RKNN 运行时会把不支持的算子自动回退 CPU）

所以嵌入式 AI 的真实功夫 = **让三种部件各干各的擅长事，并且别让数据搬运堵车**。这也解释了为什么你的 Linux/SoC 补课线（07 目录）是必修而不是选修。

## 七、加深：把「专用化」拆成可验证的规格

### 7.1 TOPS 只是峰值合同

```
有效算力 ≈ 峰值 TOPS × 利用率 × 有效精度因子
```

利用率吃：通道对不齐、算子回退、搬运堵塞、任务切换。  
**验收不能只看 datasheet 6 TOPS**，要看层形状下的 FPS / 占用率（`rknpu/load`）。

### 7.2 CPU/NPU 分工的失败模式

| 现象 | 可能原因 |
|---|---|
| NPU 很快但端到端 FPS 低 | 预处理/后处理在 CPU 堵死 |
| load 常 0 | 算子全回退 / 模型没挂上 NPU |
| 功耗高 | GPU 被误用来跑 INT8 推理 |
| 精度差 | 量化/预处理 mean-std 不一致 |

系统功夫 = **让三种 IP 各干擅长的事 + 带宽不堵**。

### 7.3 和数电/存储课怎么串

```
02：为什么要 NPU（账）
08：MAC 电路为何便宜（树深/位宽）
03：阵列如何喂饱（缓冲/数据流）
04：软件如何生成任务
```

卡住时按这条链回溯，不要孤立背 TOPS。

## 八、IC 验证视角

NPU 和 CPU 核验证气质完全不同：

- CPU 核：随机指令流、例外/中断、一致性——复杂在"控制"
- NPU：数据通路规整、模式固定——复杂在**规模**（上千 MAC 的一致性、饱和行为）和**配置组合**（每层的量化参数、tiling 参数、DMA 描述符）
- 好消息：规整结构适合形式验证（累加器链、饱和逻辑可以用 SVA 写断言全查）；坏消息：验证环境要自己生成"像神经网络"的激励（真实模型权重分布），纯随机数激不出边界
