## 一、核心一句话

**驱动 = 把硬件翻译成文件（设备节点）的一段内核代码；设备树 = 描述"这块板上有哪些硬件、接在哪"的清单文件。**
硬件（设备树）与逻辑（驱动）分离——同一个 rknpu 驱动，靠不同设备树描述，就能在 RK3588/RK3588S 各种板子上工作。

---

## 二、分层再看一遍（把前两课的图接上）

```
用户程序 ── 库调用 ── librknnrt.so ── ioctl/read/mmap（系统调用边界）── 内核 rknpu 驱动 ── 寄存器/中断/IOMMU ── NPU 硬件
                                        ↑
                              设备树告诉内核：有个 npu@fdab0000，中断是 xx，时钟是 yy
```

### 用户态 / 内核态（一句话版）

用户程序跑在低特权级，碰不了硬件；要办事就**系统调用**进内核（open/read/ioctl/mmap 都是）。驱动就是住在内核里、替你办事的代理人。NPU 的"事"主要是：分配缓冲、递交任务、等完成中断。

### /dev 节点怎么冒出来的

驱动初始化时向内核注册，内核生成设备节点：

- misc 框架 → `/dev/rknpu`
- DRM 框架（显卡界的通用框架，GEM 缓冲管理）→ `/dev/dri/renderD128` 一类的 render node

librknnrt 打开其中一个，ioctl 递交 job——"一切皆文件"在这里落到实物（第 1 课概念回收）。

## 三、设备树：硬件的"清单说明书"

### 为什么需要它

老 Linux：板级硬件信息**写死在内核代码**里（arch/arm/mach-xxx），一块板一个目录，内核臃肿。
设备树（DT）：硬件描述独立成 `.dts` 文本，**编译成 dtb 随内核一起加载**。换板子 = 换 dtb，内核二进制不动。SoC 厂商提供 SoC 级 `.dtsi`（如 rk3588s.dtsi，描述芯片内部 IP），板厂用 `.dts` **引用+修改**（我的板子使能了哪些接口、内存多大）。

### 语法五分钟（够读就行）

```
/dts-v1/;

/ {                                    ← 根节点（整块板）
    model = "Rockchip RK3588 Board";

    npu@fdab0000 {                     ← 节点：名字@寄存器基址
        compatible = "rockchip,rknpu";      ← "我是谁"→ 内核据此找驱动（匹配表）
        reg = <0x0 0xfdab0000 0x0 0x10000>, ← 寄存器区（起址+长度，可多段）
              <0x0 0xfdac0000 0x0 0x10000>,
              <0x0 0xfdad0000 0x0 0x10000>; ← 三核各 64KB（对上 03 第 3 课！）
        interrupts = <GIC_SPI …>, <…>, <…>; ← 三个核三个中断
        clocks = <&cru ACLK_NPU0>, …;       ← 时钟引用（cru=时钟控制单元）
        assigned-clock-rates = <1000000000>;← NPU 1GHz（03 第 3 课的频率来源）
        power-domains = <&power RK3588_PD_NPU>; ← 电源域（第 2 课 DVFS 的地基）
    };
};
```

- `compatible` 是驱动的"认领暗号"：rknpu 驱动里有 `of_match_table` 声明"我认 rockchip,rknpu"，内核负责把两者配对（probe）
- `reg/interrupts/clocks` 全是你天天打交道的东西，**只是从"写死在代码里的宏"搬进了"数据文件"**
- 板级 `.dts` 里 `&npu { status = "okay"; };` 这种引用语法 = "把芯片级描述的那个 npu 节点打开"

### 上板验证设备树

```bash
ls /proc/device-tree/npu@fdab0000/     # 看内核实际加载的节点（原始属性文件）
ls /proc/device-tree/ | head           # 看整板硬件清单
dtc -I fs -O dts /proc/device-tree | less   # 反编译成可读文本（dtc 需安装）
```

## 四、rknpu 驱动具体干了什么（源码目录 drivers/rknpu/）

| 文件 | 职责 | 对应你的知识 |
|---|---|---|
| rknpu_drv.c | 注册/探针、misc+DRM 双入口 | 外设 init 序列的内核版 |
| rknpu_job.c | 任务递交、完成中断处理、三核调度（core_mask/自动分配/pingpong） | DMA 描述符递交+中断收割，你熟的味道 |
| rknpu_gem.c / rknpu_mem.c | 缓冲分配（GEM / dma-heap 两种方案）、与用户态共享 | 内存管理 + cache 维护 |
| rknpu_iommu.c | 挂接 SoC IOMMU 做地址翻译 | 页表，你懂的 |
| rknpu_devfreq.c | 动态调频调压（DVFS） | 时钟/电源管理 |
| rknpu_debugger.c | debugfs 接口（version/load/freq/mm） | 验证用寄存器/状态观测点 |

**它不干的**：解析 .rknn、生成任务命令流——那在用户态 librknnrt.so（03 第 3 课）。"薄驱动、厚运行时"是这类加速器的现代设计倾向（主线 rocket 驱动开发者原话：驱动只管上电、映射缓冲、递交任务）。

### 驱动形态小知识

- 驱动可编译进内核镜像，也可做成模块（.ko）动态 `insmod`/`rmmod`——rknpu 通常编进板厂内核
- `lsmod` 看已加载模块；`dmesg` 看探针时的初始化打印

## 五、IC 验证视角（本补课线的落点）

驱动代码对你有双重价值：

1. **驱动的寄存器操作序列 = 免费的金色用法参考**：上电顺序、复位释放、时钟使能先后——驱动怎么写，通常就是芯片怎么设计的；验证环境照抄能少踩坑
2. **设备树 = 验证参数表**：频率、电压、中断号这类"配置类"内容，DV 环境的配置生成可以直接吃同一份语义
3. 调试分工口诀：**"dmesg 有错→驱动/配置；dmesg 干净结果错→硬件嫌疑大"**——和你现在"先查环境再查 DUT"的排障顺序一致
