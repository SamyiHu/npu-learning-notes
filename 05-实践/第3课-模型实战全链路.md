# 第 3 课：模型实战全链路——训练 → 完全体 → 裁剪 → 量化 → 部署 → 调试

> 编写日期：2026-11-02
> 阶段：05-实践（接在 Golden Path 之后）
> 前提：04 第 1 课（部署链路）、02 第 1 课（量化与校准）、03 第 3 课（算子回退）
> 方式：讲义 + 操作顺序 + 调试决策树。**本文只给认知地图和动手顺序，不教训练实操**（训练是另一个领域，仓库不覆盖）
> 版本口径：rknn-toolkit2 v2.3.2 / rknn-llm v1.3.0（2026-11 快照），细节以官方仓库为准

---

## 一、核心一句话

**这条链只有 5 站，而且前 4 站全在电脑上，板子只干最后一站的活。**

```
[0] 拿权重 → [1] 训练/微调 → [2] 完全体(FP32) → [3] 裁剪 → [4] 量化 → [5] 板端推理
     网上       PyTorch+GPU      ONNX 基线        PyTorch      toolkit2      librknnrt
```

新手最容易产生的误解是"板子也能剪、也能量化"。不能——**板子上只有 `librknnrt.so`（运行时），它只会 load + 推理**。量化和裁剪必须回到 PC，不是"比较好"，是板子上根本没有那套工具。

---

## 二、全景图：每一站在哪做、产出什么

```
[PC / WSL2 Ubuntu]                                        [板子]
  │
  │ ① 训练 / 微调（PyTorch，要 GPU）
  │    · 全参数微调 或 LoRA
  │    · LoRA 训完必须 merge 回主干
  ▼
model.pt ──export──► model_fp32.onnx  ◄── ② 完全体：精度参照物，永远别删
  │
  │ ③ 裁剪（PyTorch 侧改结构 → 必须重训恢复精度）
  ▼
model_pruned.pt ──export──► model.onnx
  │
  │ ④ 量化（rknn-toolkit2，吃校准集）
  │    config(target_platform='rk3576') → load_onnx → build(do_quantization=True)
  ▼
model.rknn ─────────── scp / adb ──────────────────────► ⑤ 板端推理
                                                          librknnrt 只能 load+run
```

三条必须记住的边界：

1. **训练、裁剪在 PyTorch 里做**，RKNN 工具链不做剪枝，它只吃你导出的 ONNX
2. **量化在 toolkit2 里做**（PC 端），要校准集
3. **板子只推理**，同时负责"实测"——真 FPS、真掉点、真内存

## 三、第 0 站：先破除"从头训练"这个念头

零基础最大的认知误区是"我要自己训一个模型"。现实是：

| 做法 | 干什么 | 什么时候用 | 代价 |
|---|---|---|---|
| **直接用预训练权重** | 下载官方权重，一个字不改 | 类别和官方一致（如 COCO 80 类） | 零成本 |
| **全参数微调** | 自己的数据集，所有参数更新 | 类别不同（如只检安全帽），数据几千张起 | 要 GPU，几小时~几天 |
| **LoRA / PEFT** | 冻结主干，只训一小块 | 数据少、显存小、想快速试多个版本 | 最省，但只适合大模型 |

**你现在应该在第 0 行。** Golden Path 跑的就是官方预训练的 YOLOv5s-relu，没有训练环节——这不是偷懒，这是正确顺序：**先把部署链路跑通，再回头考虑要不要训。**

## 四、第 1 站：训练与 LoRA（你说不懂的那块）

### 4.1 LoRA 到底在干什么

正常微调要更新一个大矩阵 `W`。LoRA 的思路是**不动 W，在旁边挂两个瘦长矩阵**，用它们的乘积表示"改动的量"：

```
原始：  y = W x                W 冻结，不参与训练
LoRA：  y = W x + (α/r) · B A x

W: d×k（比如 4096×4096，1677 万个数）
A: r×k（r 通常 8 / 16 / 64）
B: d×r
```

算一下参数量（d = k = 4096，r = 16）：

```
A + B = 4096×16 + 16×4096 = 131072 ≈ 13.1 万
占比  = 131072 / 16777216 ≈ 0.78%
```

**不到百分之一的参数，承担了"这次微调的全部改动"。** 于是：

- 显存暴降（不用存主干的梯度和优化器状态）
- 训练极快（只算那一小坨）
- 一个主干可以挂很多个 adapter，换 A/B 就换任务，主干共享

还有个关键设计：**训练开始时 B 初始化为 0**，所以 `BA = 0`，模型行为与原模型完全一致，从零偏移平滑起步。

### 4.2 QLoRA

把主干权重先压成 4bit（NF4）再挂 LoRA，显存再降一半，代价是慢一点。这是"消费级显卡微调 7B 模型"的标准方案。

### 4.3 ⚠️ 对本仓库最重要的一条：LoRA 必须 merge

```
训练完：W（冻结） + A,B（adapter 文件）
merge： W' = W + (α/r) · B A          ← 合成一个普通权重
导出：  W' → ONNX → 量化 → 部署
```

**RKNN 工具链不认识 LoRA adapter。** 直接把 adapter 丢给它，结果是报错或被当垃圾忽略。所以顺序永远是：

```
LoRA 训练 → merge → 导出 ONNX → 量化 → 部署
```

至于部署侧有没有"运行时挂 adapter"的玩法，以 rknn-llm 当前文档为准；**稳妥做法就是 merge 后转换**。

### 4.4 别把 LoRA 用错地方

LoRA 主要是 LLM 圈子的玩法。视觉模型（YOLO 这类）一般是直接全参数微调，或者干脆不微调——参数量本来就小，没必要省。

## 五、第 2 站：完全体 = 浮点基线

"完全体"指**没剪、没量化的原始浮点模型**，产出是 `model_fp32.onnx`（FP32）。

**它唯一的作用是当参照物。** 后面每一步优化都会掉精度，你必须有个东西能回答"到底掉了多少"。

> **铁律：`model_fp32.onnx` 永远留在硬盘上，不许删、不许覆盖、不许"优化完就清理"。**

没有基线，`accuracy_analysis` 报的余弦相似度你也不知道该跟谁比。

## 六、第 3 站：裁剪

### 6.1 三种"裁剪"，别混

| 类型 | 做法 | 效果 | 建议 |
|---|---|---|---|
| **非结构化剪枝** | 把不重要的单个权重置 0 | 模型变小、变稀疏 | 工具链不一定吃得到加速，**先别碰** |
| **结构化剪枝** | 整个通道 / 整层删掉 | 真的减少计算量 | 要重训恢复精度，进阶再说 |
| **蒸馏** | 大模型教小模型 | 换小模型但精度接近 | 换模型时的备选 |

### 6.2 关于"稀疏"的诚实提醒

RK3576 的 **6 TOPS 是稀疏口径**（datasheet 脚注带星号，见 05 上手指引 §1）。硬件支持稀疏推理，不等于你的剪枝结果能自动换来加速：

- 剪出来的稀疏模式（2:4？块稀疏？）如果对不上硬件要求的格式，**只是省了内存，时间一点没省**
- 工具链是否生成硬件认可的稀疏格式，本仓库**尚未实测**，别先入为主

### 6.3 顺序铁律

```
剪枝（改结构） → 重训恢复精度 → 导出 ONNX → 量化
```

反过来（先量化再剪）没意义：剪完结构变了，量化参数全部作废，得重新量化。

### 6.4 给你的判断

**你现在连 INT8 量化掉多少点都还没测过，先别裁。** 裁剪是"量化之后精度还是不够、或性能还是不够"时才上的第二把刀。

## 七、第 4 站：量化

### 7.1 RKNN 走的是 PTQ，不是 QAT

| | PTQ（训练后量化） | QAT（量化感知训练） |
|---|---|---|
| 做法 | 模型训好，拿几百张图跑一遍统计激活范围 | 训练时模拟量化误差 |
| 要不要重训 | 不用 | 要 |
| 精度 | 够用 | 更好 |
| RKNN 支持 | ✅ `build(do_quantization=True)` | ❌ toolkit2 不做 |

### 7.2 实际代码（和 Golden Path 同款）

```python
rknn.config(target_platform='rk3576', quantized_dtype='w8a8')   # LLM 用 'w4a16'
rknn.load_onnx('model.onnx')
rknn.build(do_quantization=True, dataset='./calib_list.txt')    # ← 量化发生在这里
rknn.export_rknn('model.rknn')
```

### 7.3 校准集是量化的命门

| 要求 | 说明 |
|---|---|
| 数量 | 100~300 张（覆盖度比数量重要） |
| 来源 | **必须来自你的真实场景**（拿 ImageNet 校准工业检测必崩） |
| 覆盖 | 光照、角度、尺度都要有，别全挑最清楚的 |

02 第 1 课那句总结仍然成立：**校准集决定 s；s 错了，整层一起错。**

### 7.4 精度掉了的救援阶梯

```
换校准集 → accuracy_analysis 定位 → 混合量化（敏感层留 FP16） → 换模型
```

RK3576 还有个独门选项：`quantized_dtype='w4a16'`（权重 4bit + 激活 FP16，group 32/64/128），**仅 RK3576/RV1126B 支持（v2.3.0+）**。LLM 上官方推荐它而非 w8a8（05 上手指引 §6 有数据）。

## 九、调试链路：四层，从下往上查

出问题时**不要连续换命令**（Golden Path README 那句是对的）。按顺序走，每层只问一个问题。

### L0 版本对齐（最先查，多数怪问题在这）

| 组件 | 在哪 | 怎么查 |
|---|---|---|
| rknn-toolkit2 | PC (WSL2) | `pip show rknn-toolkit2` |
| librknnrt.so | 板子 | `strings /usr/lib/librknnrt.so \| grep -i version` |
| rknpu 驱动 | 板子 | `cat /sys/kernel/debug/rknpu/version` |

**三者必须同代**（本仓库验证 v2.3.2 / 驱动 0.9.8）。不齐的典型报错：`driver version too low`、`Query platform error`。修法是升/降版本，**不是改代码**。

### L1 转换正确性（模型能不能生成）

问：`.rknn` 生成成功了吗？报错就看三件事：

1. **算子不支持** → 报错会点名哪个 op。解法：换等价写法。airockchip 的 YOLOv5s-**relu** 版就是把激活换成 ReLU 的优化版，基准表里 65.0 FPS 比原版 57.5 还快
2. **shape 不对** → ONNX 导出时固定输入尺寸。RKNN 对动态 shape 支持很弱，务必把 `dynamic_axes` 设死或不设
3. **ONNX 本身有问题** → 先 `onnx.checker.check_model()`，再用 `netron` 看一眼结构

### L2 精度（最常见的战场）

**核心方法：三方对齐。**

```
A. PC 跑 FP32 ONNX              ← 真值
B. PC 跑 INT8 仿真 rknn.inference ← 只含量化损失
C. 板子跑 INT8 .rknn             ← 量化损失 + 部署损失
```

- **A vs B**：差多少 = 量化掉的点 → 走 §7.4 救援阶梯
- **B vs C**：差多少 = 部署环节引入的问题 → **先怀疑预处理，别怀疑模型**

预处理对照表（第一大坑，逐行对）：

| 检查项 | PC 端常见 | 板端 demo 常见 |
|---|---|---|
| resize 算法 | PIL `bilinear` | OpenCV `INTER_LINEAR` |
| letterbox 填充 | 补灰 114 | 补黑 0 |
| 通道顺序 | RGB | BGR（OpenCV 默认） |
| 归一化 | `[0,1]` | mean/std 手写错 |

同一张图，PIL resize 和 OpenCV resize 出来的像素就不一样，量化模型对这种差异很敏感。做法：**两边逐行对照预处理代码**，或者干脆用同一份 C 代码在两边跑。

**定位不到时的笨办法（有效）**：把网络截断——只保留前 10 层导出一个临时 ONNX，两边跑同一输入比中间层输出，一层层往后挪，精确到层。

### L3 性能（跑通了但不快）

1. **PC 先定位**：`rknn.eval_perf()` 拿逐层耗时表，看哪层占大头；日志里标了 CPU 的就是回退
2. **板端拿真值**：`/sys/kernel/debug/rknpu/load` 是**瞬时占用率**，不是利用率，别拿它当性能指标
3. **核配置**：`rknn_set_core_mask(ctx, RKNN_NPU_CORE_0_1)`，预期加速比明显小于 2×（03 第 3 课讲过的协同开销）
4. **量化类型**：视觉模型一般 `w8a8`，LLM 走 `w4a16`

## 十、给你板子的最小可行路线（还没完整跑过就从这里开始）

你现在已经跑通 YOLOv5s 转换+部署（2026-09-10 实录）。接下来的顺序：

```
① 不训练，继续用官方权重            ← 别自己造模型
② 把 model_fp32.onnx 单独存一份基线  ← 以后所有对比都靠它
③ 做两组对比实验：
   INT8 单核 → 记 FPS + mAP
   INT8 双核 → 记 FPS + mAP + 加速比
④ 故意做一次"坏的量化"：
   拿 ImageNet 图当校准集去量化检测模型
   → 用 accuracy_analysis 找出崩的层
   → 这就是最好的调试练习
⑤ 想玩 LLM：Qwen2-0.5B → rknn-llm w4a16 → 板端 tok/s
   （LoRA 那套暂时不用碰，等你有"想改模型行为"的需求再说）
```

**第 ④ 步特别值得做**——主动制造一个 bug 再修好它，比顺风顺水跑通十次学得多。它把 §7.3、§9 L2 一次性练完。

## 小白练习与答案 · 模型实战全链路
> 每题都要求写出过程或排查顺序；不要只写“懂了”。

**计算 1**：`d=k=4096`、`r=8` 时，LoRA 的 A+B 有多少参数？占原矩阵多少？

<details>
<summary>答案</summary>

A+B = 2 × 4096 × 8 = 65536，占 16777216 的约 0.39%。

</details>

**解释 2**：为什么先剪枝再量化，不能反过来？

<details>
<summary>答案</summary>

剪枝改变模型结构，已写入 .rknn 的量化参数（逐层 scale/zero-point）会全部失效，必须重新量化；先量化再剪等于白做一遍。

</details>

**调试 3**：PC 上 INT8 仿真结果正常，板端结果全错。第一步查什么？

<details>
<summary>答案</summary>

查预处理是否一致（resize 算法、letterbox 填充值、RGB/BGR、归一化），再查模型文件和运行时版本。

</details>

**判断 4**：同事说"我们剪了 50% 权重，NPU 一定快一倍"。这句话哪里有问题？

<details>
<summary>答案</summary>

非结构化剪枝只是让权重变稀疏，能否加速取决于稀疏格式是否匹配硬件要求、工具链是否生成对应任务描述；不匹配时只省内存不省时间。另外加速还受内存带宽和利用率限制。

</details>
