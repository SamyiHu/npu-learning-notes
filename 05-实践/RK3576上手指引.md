## 一、认知校准：RK3576 关键规格（2026-08 核实版）

| 项 | 规格 | 备注/出处 |
|---|---|---|
| NPU 算力 | 6 TOPS@INT8 | **datasheet 星号脚注 = Sparsity（稀疏口径）**，宣传页不提 |
| NPU 结构 | **双核**，可独立或协同 | 官方 datasheet 原文 "dual core co-work, or work independently" |
| NPU 数据类型 | INT4/INT8/INT16/FP16/BF16/TF32 | RKNPU2 世代（rknn-toolkit2 v2 工具链） |
| CPU | 4×A72@2.2G + 4×A53（+M0 协核） | A53 频率板厂两说 1.8/2.0G，官方未单列 |
| GPU | Mali-G52 MC3 | |
| 内存 | LPDDR4/4X/5，32bit，最大 16GB | 32bit 位宽 = DDR 带宽天花板（03 第 2 课的账） |
| RGA | **2× RGA2-Pro**（不是 RGA3） | 目的端最大 8192×8192、40bit IOMMU |
| 制程 | 8nm | 官方口径"第二代 8nm" |
| NPU 基址 | 0x27700000 | 对照 RK3588 的 0xfdab0000；dmesg 横幅可见 |

### 双核的证据链（IC 验证式核对，三条独立来源一致）

1. 官方 datasheet Rev 1.0 原文："dual core, co-work or independently"
2. BSP 设备树 `rk3576.dtsi`：`npu@27700000`（compatible `rockchip,rk3576-rknpu`），**双中断 npu0_irq/npu1_irq、双电源域 NPU0/NPU1、双时钟 aclk0/aclk1**——和 3588 的三段式结构同款思路，少一核
3. Toolkit2 v2.3.2 API 文档原话："RK3576 has only 2 cores, so NPU_CORE_2 and NPU_CORE_0_1_2 cannot be set"

### 与旧讲义的 4 处修正（对应课程文件已同步更新）

| 原讲义说法 | 核实结论 |
|---|---|
| 03/第3课："core_mask 官方仅支持 RK3588，RK3576 按单 NPU 用" | **错**。RK3576 双核支持 core_mask：`NPU_CORE_0` / `_1` / `_0_1`（无 `_2`、`_0_1_2`）；C API 文档明确 "works at RK3588 and RK3576" |
| 选型指南/03 课表格："1 核（厂商称双核，待确认）" | 已确认**双核**（上表证据链） |
| 想当然认为 RK3576 是 RGA3 | 实为 **2× RGA2-Pro**（librga 官方开发者指南芯片对照表）；RK3588 才是 RGA3+RGA2E 共存 |
| "6 TOPS" 直接对标 3588 | 6T 是稀疏口径；实测吞吐约为 RK3588 的 **55~70%**（官方 issue #448 回复：3588 三核 + CPU 更强） |

## 二、到手前准备清单

**硬件**（本板 DshanPi-A1 要求，见第 3 节表）：

- [ ] **电源：Type-C PD ≥30W（本板硬性要求，严禁非 PD 或 <30W**——官方明说不稳/重启且不保修；上电自动开机）
- [ ] **Type-C 3.2 10Gbps 数据线**（本板烧录 eMMC 官方要求；劣质线是识别不到设备的第一嫌疑）
- [ ] 散热：板载风扇接口（正负极防呆），NPU 长跑发热明显
- [ ] 网线或 WiFi 环境（本板双千兆 + WiFi6，联调靠 ssh/adb）
- [ ] （可选）USB 转串口：波特率 **1500000**，推荐 CH343/FT232，不推荐 PL2303/CH340
- [ ] （仅无 eMMC 版）一张高速 TF 卡作系统盘

**软件**（Windows 侧）：

- [ ] 本板直链（dl.100ask.net/Hardware/MPU/RK3576-DshanPi-A1/，免登录）：**DriverAssistant v5.1.1 + RKDevTool v3.32** + 引导 Loader（rk3576_spl_loader_v1.09.107.bin，随镜像发布）

- [ ] （卡刷备选）SDDiskTool **v1.78+**（RK3576 要求）或 balenaEtcher
- [ ] WSL2 + rknn-toolkit2 v2.3.2 环境（07 补课线第 1 课已备；**百问网 RKNN 教程 3-3-1 也是 v2.3.2，两边命令可互抄**），Linaro GCC 6.3.1 交叉工具链（model zoo 官方推荐）

**认知准备**：去你板厂的文档站把"快速开始 + 烧录固件"两页先读一遍（第 3 节有链接表）。

## 四、开箱四步（Day 1）

### 1. 烧录/确认系统

本板出厂已烧 ArmbianOS（带 NPU），可跳过烧录直接开机；要重刷时两条路：

- **整包固件**（推荐新手）：dl.100ask.net 下载 ArmbianOS V1.0 → RKDevTool "升级固件"页加载（Loader 用官方配套的 rk3576_spl_loader_v1.09.107.bin）→ 板子进烧录模式 → 执行
- **进烧录模式**（通用操作）：Type-C 3.2 10Gbps 线接板 **OTG 口**直连 PC（勿经 HUB）→ 断电按住 **Recovery**（Loader 模式）或 **Maskrom** 键 → 上电 → RKDevTool 显示"发现一个 LOADER/MASKROM 设备"后松开。若板无 Maskrom 键：短接 ADC 测试点与 GND 再上电（Luckfox 官方即此法）

识别不到设备时先怀疑：劣质线（本板烧录明确要求 10Gbps 线）/ USB 口供电 / RKDevTool 版本过旧 / Type-C 插错了口。

### 2. 开机自查（对应 04 第 2 课"排查三件套"）

```bash
cat /proc/rknpu/version      # 期望 ≥0.9.8（RKLLM 硬门槛；0.9.6/0.9.7 会有告警）
dmesg | grep -i rknpu        # 期望看到 "[drm] Initialized rknpu 0.9.x ... for 27700000.npu"
ls /dev/dri/ /dev/rknpu      # 设备节点存在（renderD + rknpu）
cat /sys/kernel/debug/rknpu/load   # NPU 占用率（此时应为 0%）
```

板厂镜像若出厂驱动 <0.9.8：先去文档站找新固件整包重刷（RKLLM 实验的前置条件）。

### 3. 联网 + ssh

本板首次启动是**图形向导**（需接显示器+键鼠）：设 root 密码（默认示例 100ask）、选 Bash、建普通用户、连 WiFi、时区，完成后进 GNOME 桌面（记得关掉自动休眠，官方文档有 gsettings 命令）。之后 `ip a` 拿 IP，Windows 直接 `ssh`。串口留作救砖后备。

### 4. 版本配套自查（第一大坑，写进肌肉记忆）

```bash
strings /usr/lib/librknnrt.so | grep -i version    # 板端运行时版本
```

铁律：**PC 端 toolkit2 = 板端 librknnrt.so = 板端 rknn_server，三者同版本**（v2.3.2）。版本不齐的典型报错就是 dmesg/程序里的 "driver version too low / Query platform error"。

## 五、第一个模型：YOLOv5s 全链路（阶段四课程实操化）

PC（WSL）侧：

```bash
git clone https://github.com/airockchip/rknn_model_zoo
cd rknn_model_zoo/examples/yolov5/python
python3 convert.py rk3576          # 转换+INT8 量化，target_platform='rk3576'
cd ../cpp
./build-linux.sh -t rk3576 -a aarch64   # 交叉编译板端 demo（Linaro GCC 6.3.1）
```

板端（adb 或 scp）：

```bash
adb push install/rknn_yolov5_demo_Linux /userdata/
cd /userdata/rknn_yolov5_demo_Linux && ./rknn_yolov5_test_model model/RK3576/yolov5s-640-640.rknn model.jpg
cat /sys/kernel/debug/rknpu/load     # 跑的时刻占用率应不再是 0
```

（每条命令的知识点都在 04 两课里：convert=build 量化，push=部署，run=librknnrt 七步流，load=验证真跑在 NPU 上。）

**性能预期**（rknn_model_zoo 官方基准，RK3576 单核、NPU 满频、INT8，纯推理不含前后处理）：

| 模型 | RK3576 单核 FPS | RK3588 单核（对照） |
|---|---|---|
| MobileNetV2 | 467.0 | 713.7 |
| ResNet50 | 99.0 | 134.0 |
| YOLOv5s | 57.5 | 91.9 |
| YOLOv5s-relu | 65.0 | 96.6 |
| YOLOv8n / 8s | 90.2 / 40.8 | 136.8 / 64.8 |
| PP-OCRv4 det/rec | 64.3 / 96.8(rec 为 FP16) | 94.0 / 139.7 |

比值稳定在 3588 的 ~65%——"标称同 6T、实测差三成"的原因（3588 单核算力更高 + CPU/带宽更强）这就是活生生的"TOPS ≠ 吞吐"教材（02 第 2 课）。

**到手后第一个实验：双核 core_mask**（03 第 3 课多核玩法的 RK3576 版）：

```c
// 方案A：单模型吃双核
rknn_set_core_mask(ctx, RKNN_NPU_CORE_0_1);
// 方案B：两个模型各绑一核并行（检测+分割互不干扰）
rknn_set_core_mask(ctx_a, RKNN_NPU_CORE_0);
rknn_set_core_mask(ctx_b, RKNN_NPU_CORE_1);
```

记录：单核 vs 双核 FPS 加速比（预期：明显小于 2×，跨核协同的账在 03 第 3 课讲过）；两模型并行时各自 FPS 是否稳住。

## 六、LLM 实验（阶段六联动，RK3576 完整支持）

版本事实（2026-08）：**rknn-llm v1.3.0**（2026-06-17 发布），RK3576 自 v1.0.x 首发即支持；v1.3.0 还专门优化了 RK3576 长上下文解码。**rknpu 驱动 ≥0.9.8 是硬门槛**（CHANGELOG 原文 + Firefly/Radxa 文档一致）。

**性能预期**（官方 benchmark.md，w4a16、上下文 4096、NPU/CPU 满频）：

| 模型 | RK3576 tok/s (NPU) | 内存峰值 | RK3588 w8a8 参照 |
|---|---|---|---|
| Qwen2.5-0.5B | 20.8 | 0.8 GB | 34.6 |
| Qwen2.5-1.5B | 20.4 | 1.4 GB | 25.9 |
| Qwen2.5-3B | 14.5 | 2.2 GB | 19.1 |
| Qwen2.5-7B | 9.2 | 4.5 GB | 13.0 |
| DeepSeek-R1-Distill-Qwen-7B | 8.2 | 4.9 GB | 12.5 |
| Qwen2.5-VL-3B（多模态 w8a8） | 6.3 | 2.5 GB | 9.2 |

选型建议（按你板子内存；**DshanPi-A1 是 6G/8G 两档**）：6G 板 ≤3B 可跑（3B 峰值 2.2G，系统占 1G 多，别开桌面跑）；8G 板 3B 舒适、7B 勉强（系统还要占内存）；16G 板 7B 无压力（本板没有 16G 版）。官方 benchmark 覆盖到 8B 封顶，14B+ 是 3588 专属。百问网 3-4 章（DeepSeek-R1/Qwen-VL）就是这条线的实操教材。

三个 RK3576 专属知识点：

1. **官方推荐 w4a16，不推荐 w8a8**——与 RK3588 相反（3576 上 Qwen2.5-1.5B：w4a16 20.4 vs w8a8 17.4 tok/s）。原因与 02 第 1 课 W4 权重量化 + FP16 激活 的数据通路有关，值得实测后想想为什么
2. 转换参数：`target_platform='RK3576'`；`num_npu_core` 官方只示例了 3588 填 3，RK3576 未明示（双核大概率 2，到手实测确认——记进你的问答收录）
3. 官方转换好的 .rkllm 模型放联想网盘（console.box.lenovo.com/l/l0tXb8，提取码 rkllm），文件名带 `_rk3576` 后缀的才是给你的；多模态的 vision encoder 是另一个 .rknn，也要选 rk3576 版

已知坑（GitHub issues 实录）：

- "Query platform error!" → runtime 太旧，驱动和 librkllmrt 一起升（issue #154）
- 多模态 demo 崩溃/无输出 → demo 源码里 IMAGE_WIDTH/EMBED_SIZE 等常量要按模型手改重编译（#336/#341）；纯文本正常多模态无输出 → max_context 调大（#330）
- 8G 板跑 MiniCPM-V-2.6 吃力（双模型同载）→ 多模态按 2×内存预估

## 八、坑清单（集中版，按踩中概率排序）

1. **版本配套**：toolkit2 / librknnrt / rknn_server 同版本；驱动 ≥0.9.8（RKLLM）——报错先查这三件
2. **刷错系统 NPU 没了**：认准 dl.100ask.net 官方镜像——百问网"ArmbianOS"带 NPU✅，但 armbian.com 社区通用镜像/主线内核**不带**（rocket 驱动不支持 RK3576）；OpenEuler/Fedora 官方包也暂无 NPU
3. **RKDevTool <3.30 不识别设备**（本板配套 v3.32 没问题）；SDDiskTool <1.78 做的卡启动不了
4. **供电与线材**：本板 PD ≥30W 是硬性要求；烧录线要 Type-C 3.2 10Gbps，劣质线是第一嫌疑
5. **6 TOPS 预期管理**：稀疏口径 + 双核≠2×单核 + 32bit 内存位宽，三重折扣都正常
6. rkllm 的 .rkllm/.rknn 文件必须选 rk3576 编译版（3588 编的不通用，04 第 1 课"绑定芯片"的又一实例）
7. 板厂镜像驱动过旧 → 别单独换驱动，整包升级固件（驱动/内核/运行时是配套发版）

## 十、开箱实录（2026-09-09）：显示、远程、运行时三坑全记录

> 板子到手首日实战，三个坑全踩全修。以下每条都是本板实测，不是转抄。

### 坑 ①：HDMI 无输出（根因：厂商内核 PHY bug，非硬件）

- **现象**：5 寸屏（原生 1024x600@60）接板子无信号，同一块屏接 PC 正常点亮。
- **定位链**：`cat /sys/kernel/debug/dri/0/summary` 显示 CRTC "ACTIVE"（假象）→ `dmesg` 真相：`hdptx phy lane can't ready!` + `phy poweron failed --> -22`。**RK3576 的 hdptx PHY 在 50.25MHz（1024x600@60）锁不住 lane，HDMI 发射器根本没发信号**。DRM 状态机的 ACTIVE 不代表物理层在工作。
- **规律**：74.25MHz（720p60）能锁、50.25MHz 必败——低像素时钟 PLL 参数缺失/错误，纯软件 bug。
- **修法**（当前生效，重启不丢）：
  1. `/boot/armbianEnv.txt` 加 `extraargs=video=HDMI-A-1:1280x720@60e` → 控制台 720p 锁定；
  2. GNOME(Wayland) 会自作主张切回 EDID 首选 1024x600 重新踩雷 → 改走 X11：`/etc/gdm3/custom.conf` 设 `WaylandEnable=false`，`/etc/X11/xorg.conf.d/10-monitor.conf` 写死 720p Modeline + `Option "kmsdev" "/dev/dri/card0"`（多 DRM 卡设备必须显式指定，否则 Xorg 报 "Cannot run in framebuffer mode" 起不来）。
- **注意**：`drm.edid_firmware` EDID 覆盖在本板**无效**（厂商 dw-hdmi 驱动绕过 DRM 核心自读 DDC），别在这条路上浪费时间；`drm.edid_firmware=xxx:none` 语法在本内核也只是把 "none" 当文件名报 -2。
- **原生 1024x600 的正道**：等板厂新固件/Armbian 更新 vendor 内核（已具备向百问网 QQ 群 798273638 报 bug 的完整证据）。5 寸屏 720p 缩放显示视觉差异很小，不堵路。

### 坑 ②：远程访问（VNC 方案落地，RDP 放弃）

- **这台镜像 gdm 默认不自启**（display-manager.service 链接缺失）——文档说的"首次图形向导"实际没跑起来，首次开机是 tty1 的 armbian 文本向导。修复：`ln -s /usr/lib/systemd/system/gdm.service /etc/systemd/system/display-manager.service`。
- **armbian-firstlogin 会劫持一切登录入口**：xrdp/VNC 之外的 startwm.sh 都先卡在它上面（等永远等不到的交互输入）。跳过方法：`rm /root/.not_logged_in_yet`。
- **xrdp + GNOME 黑屏**：服务端渲染正常（modetest/截屏可证）但客户端全黑，MobaXterm 与 mstsc 双双复现，xrdp 编码通道问题，放弃。**改用 x11vnc 镜像控制台**（`/usr/local/bin/x11vnc-console.sh` + systemd 服务，动态发现 X display 和 -auth 路径，`-noshm` 绕开本板 SHM BadAccess，XDamage 增量更新省流量，`-xkb` 修键盘映射）。端口 5900，密码 100ask。
- **本板 SHM 结论**：x11vnc 无论以 root 还是同 uid 用户跑，X_ShmAttach 一律 BadAccess（root 建 0600 段、dev 的 Xorg 挂不上；同 uid 也复现）——`-noshm` 是刚需。
- **账号格局**：桌面自动登录 `dev`/`100ask`（GDM PAM 禁止 root 自动登录，`user != root`，别硬刚）；ssh/SFTP 用 `root`/`100ask`。自动登录、永久不熄屏（/etc/dconf）均已持久化。
- **全有线才流畅**：板子网线只覆盖"板→路由"，PC 走 WiFi 到路由照样卡。PC 网线插同一路由器后 ping 1ms 恒定，体验质变。

### 坑 ②b：控制台桌面全黑（Panfrost 渲染不落地，2026-09-09 深夜）

- 修复熄屏后桌面仍全黑。证据三分法定位：HDMI 信号 ACTIVE 无 PHY 错（非坑①复发）、`gnome-shell` 存活、**服务端 scrot 截屏纯黑（2.7KB 纯色图）** → 问题在 X 画面缓冲区本身。
- 排除法：GLX 正常（glxinfo 直连渲染、Mali-G52 Panfrost 硬件加速 yes）→ 矛盾点 = **Panfrost 渲染的 buffer 与显示控制器之间的共享在这套 vendor 内核上不落地**：GPU 画了，屏幕看不见。
- 修法（部分生效）：`/etc/X11/Xsession.d/95libgl-software` 写入 `export LIBGL_ALWAYS_SOFTWARE=1` 强制 CPU 软件渲染（llvmpipe），重启 gdm3 后**面板已出画面（部分显示，待续）**。720p 软件渲染对 A72 无压力。
- 待办：确认"部分显示"的剩余问题（疑似刷新不完整/性能）；观察 ssh 间歇性 EOF 是否与 PC 双网卡（WiFi+有线同网段，WiFi 已断开）或板端驱动相关。

### 坑 ③：板端运行时缺装（已补齐）

- 出厂镜像（ArmbianOS V1.0，内核 6.1.115-vendor-rk35xx，2025-09-03 版）**只有内核驱动，没有用户态运行时**：`/usr/lib/librknnrt.so` 和 `rknn_server` 均不存在，dpkg 里也无 rknn 包。
- 已装：`librknnrt.so v2.3.2`（GitHub airockchip/rknn-toolkit2 tag v2.3.2，放 /usr/lib + ldconfig，`strings` 验证 `librknnrt version: 2.3.2`）。板子直连 GitHub 下载速度可接受（7.4MB/7s）。
- 铁律对齐进度：驱动 0.9.8 ✅ / librknnrt 2.3.2 ✅ / **PC 端 toolkit2 2.3.2 ❌（WSL 连发行版都没装，下一里程碑的前置）**。
- 版本查询的小坑：`/proc/rknpu/version` 在本板不存在，驱动版本看 `/sys/kernel/debug/rknpu/version`（`RKNPU driver: v0.9.8`）；双核实锤：`cat /sys/kernel/debug/rknpu/load` 输出 `Core0/Core1` 两列。

### 第一个模型全链路实录（2026-09-10 跑通，环境与命令存档）

- PC 侧：WSL2 Ubuntu 24.04（py3.12 venv）+ `pip install rknn-toolkit2==2.3.2 setuptools<81 onnx==1.16.1`（**py3.12 双坑**：setuptools≥81 无 pkg_resources、onnx≥1.17 无 mapping，须钉版本）+ `git clone --depth 1` airockchip 的 rknn-toolkit2(v2.3.2 tag) 与 rknn_model_zoo。
- 转换：`examples/yolov5/model/download_model.sh` 下 yolov5s_relu.onnx（airockchip 优化版，联想网盘 CDN 国内快）→ `python convert.py ../model/yolov5s_relu.onnx rk3576 i8`（校准集 coco_subset_20 已含在仓库，无需另下）→ `yolov5.rknn`。
- 编译：`apt install cmake g++-aarch64-linux-gnu`（g++ 交叉包独立，别只装 gcc 包）→ model zoo 根目录 `GCC_COMPILER=aarch64-linux-gnu bash build-linux.sh -t rk3576 -a aarch64 -d yolov5` → `install/rk3576_linux_aarch64/rknn_yolov5_demo/`（二进制+模型+bus.jpg+库，动态依赖仅 libc/libstdc++/librknnrt）。
- 部署运行：`sshpass scp -r` 推到板 `/root/rknn_yolov5_demo` → `LD_LIBRARY_PATH=lib ./rknn_yolov5_demo model/yolov5.rknn model/bus.jpg` → 检出 person×3 + bus（最高置信 0.88），结果写 out.png。
- **NPU 实证**：连续推理时 `cat /sys/kernel/debug/rknpu/load` → `Core0: 5~8%, Core1: 0%`（默认单核，正常）；5 次全流程（含进程启动+模型加载）共 2.1s。
