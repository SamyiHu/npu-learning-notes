## 一、核心一句话

**RKNPU 是"任务列表驱动"的固定功能加速器：用户态运行时库（librknnrt）把模型编译成一串任务/命令，内核驱动只管上电、分配缓冲、递交任务；硬件逐条执行。**
它不是一颗"会跑指令的 CPU"，是一条**为神经网络配置好的专用流水线**。

---

## 二、RK3588 的 NPU：3 个真·独立核

官方规格：6 TOPS@INT8，三核（triple core）。内核源码/设备树层面的证据链：

```
每核各自：64KB 寄存器区（基址 0xfdab0000 / 0xfdac0000 / 0xfdad0000）
          独立中断 npu0/1/2_irq
          独立时钟（ACLK/HCLK）、独立电源域（npu0/npu1/npu2）
共享：    一个 IOMMU（rockchip iommu v2 @ 0xfdab9000）做地址翻译
每核算力：1024 INT8 MAC/拍 × ~1GHz ≈ 2 TOPS（TRM 转述+社区核对）
```

### 分核调用（core_mask）——RK3588（3 核）与 RK3576（2 核）能玩

SDK 的 `rknn_set_core_mask()` / `rknn_init` 的 flag：

```
RKNN_NPU_CORE_0 / _1 / _2      绑定单核
RKNN_NPU_CORE_0_1 / _0_1_2     双核、三核联合
RKNN_NPU_CORE_AUTO              驱动自动分配（0）
（RK3576 双核只有 _0 / _1 / _0_1，无 _2 与 _0_1_2——API 文档原文）
```

两种用法：

1. **多模型并行**：三个模型各绑一个核——一个检测行人、一个检测车牌、一个跑人脸，互不干扰（嵌入式多任务 AI 的经典玩法）
2. **单模型多核**：0_1_2 联合跑一个大模型。注意：实测加速有限（跨核协同路径基本没被闭源运行时用起来），**别把 6 TOPS 当成一个 6T 的大核期待**

注：RK3588S 的 NPU 与 RK3588 相同（3 核），旧驱动上 core_mask 表现异常，驱动 ≥0.9.6 才正常。RK3576 是**双核 NPU**（官方 datasheet："dual core co-work, or work independently"；BSP 设备树 `npu@27700000` 双中断/双电源域佐证），core_mask 同样可用，但只有 `NPU_CORE_0 / _1 / _0_1`——多模型绑核实验在 RK3576 上是"双核版"。2026-08 核实，详见《05-实践/RK3576上手指引》。

## 三、RKNPU 各代数据类型（选型/量化能力对照）

| 芯片 | NPU 算力 | 核 | 支持类型 | 对量化的意义 |
|---|---|---|---|---|
| RK3566 / RK3568 | 1 TOPS | 1 | INT8 / INT16 | 只能整数量化；精度不够只能靠混合"INT16"扛 |
| RK3562 | 1 TOPS | 1 | INT8（INT16 待确认） | 同上，入门档 |
| RK3576 | 6 TOPS* | 2（官方确认，可独立/协同） | INT4/INT8/INT16/FP16/BF16/TF32 | 混合量化可留 FP16 层；W4A16/FlashAttention/稀疏推理独占（*6T 为稀疏口径，实测吞吐约为 3588 的 55~70%） |
| RK3588 / S | 6 TOPS | 3 | INT4/INT8/INT16/FP16/BF16/TF32（官方） | 同上 + 三核并行 |
| RV1103 / RV1106 | 0.5 TOPS | 1 | INT4/INT8/INT16 | 摄像头小芯片，能跑轻量模型 |

（第 1 课"混合量化救援阶梯"里"RK3566/3568 没有 FP16 可留"就是这张表的伏笔。）

## 四、它怎么工作：一条推理的全旅程

把阶段二、三的知识串成一条线（RK3588 上跑 YOLO 为例）：

```
[PC 端] RKNN-Toolkit2：ONNX → 量化 → 编译成 .rknn（权重+任务描述）
                        │  (adb 传到板子)
[板端用户态] 你的程序调用 librknnrt.so：
    rknn_init()   → 库解析 .rknn，生成 NPU 任务列表（每层一段命令流）
    rknn_run()    → 库通过 ioctl 把 job 递给内核驱动
[板端内核态] rknpu 驱动：
    上电/调频（电源域+devfreq）→ 映射缓冲（IOMMU 建页表）→ 提交 job 给 NPU 前端
[硬件] NPU 前端单元逐条执行任务列表：
    DMA 搬权重/激活进片上缓冲 → MAC 阵列算卷积 → 激活/池化/量化单元 → 写回
[回到用户态] rknn_outputs_get() 取输出（INT8+scale）→ CPU 反量化+后处理
```

三个关键认知：

1. **重活都在用户态闭源库 librknnrt.so**：模型→命令流的"编译器"在库里。内核驱动很薄，官方说法是"只管上电、映射缓冲、递交任务"（主线上游开发者原话），连固件都不加载——和 GPU 那种"带固件的处理器"是两种流派
2. **没有公开指令集**：任务列表格式未公开文档化（TRM 第 36 章只有寄存器级描述）。社区正在逆向（Mesa "Teflon" 项目、rocket 驱动），这也是"开源 NPU 栈"的前沿话题
3. **算子不在硬件清单里 → 运行时自动回退 CPU**：表现为"NPU 占用率不满、CPU 旁路忙"，排查部署问题的常识

### 血统冷知识

老一代 RK1808/RK3399Pro 直接用 NVIDIA 开源的 **NVDLA**；RK3588 这代是瑞芯微在 NVDLA 基础上的自研变形（LWN 上游邮件列表原话）。所以你在 RKNPU 里能看到 NVDLA 风格的"卷积加速、数据/平面处理"等固定功能单元划分——第 1 课那张框图不是虚构的。

| 项 | 数值 | 可信度 |
|---|---|---|
| 每核 MAC | 1024 INT8 MAC/拍（FP16 时 512） | TRM 社区转述+逆向核对 |

## 六、驱动与调试接口（板端 map，阶段四会用到）

```
内核驱动   drivers/rknpu/（DRM 框架，render node 形如 /dev/dri/renderD128，
           另有 misc 设备 /dev/rknpu）
查驱动版本 cat /proc/rknpu/version          （如 RKNPU driver v0.9.8）
看 NPU 占用 cat /sys/kernel/debug/rknpu/load
看频率/电压 /sys/kernel/debug/rknpu/{freq,volt,power}
SRAM 状态   /sys/kernel/debug/rknpu/mm
```

主线内核另有社区驱动的 `drivers/accel/rocket`（DRM accel 框架）+ Mesa 用户态栈，属"开源替代路线"，目前生产生态仍以 vendor 驱动为主。**驱动版本、librknnrt 版本、工具链版本三者要配套**——版本不匹配是新手第一大坑。

## 七、IC 验证视角（本阶段的"如果让我测"）

RKNPU 这类"任务驱动型加速器"的验证清单，拿去对量：

1. **任务递交握手**：前端忙碌时递交、连发多 job 的乱序完成、异常任务的丢弃与恢复
2. **IOMMU 配合**：页表翻译错误、跨页缓冲、非法地址访问会不会挂总线
3. **多核资源**：三核并发时共享部件（IOMMU、DDR 端口）的仲裁与隔离；单核复位不影响他核
4. **数值一致性**：同一任务在不同核/不同分核模式下，输出逐 bit 一致吗（应当一致）
5. **电源域**：运行中关电/调频（devfreq 每秒都在做的事）时的数据完整性
6. 激励生成思路：录制真实模型的"任务流"做回放验证——比随机生成有效得多
