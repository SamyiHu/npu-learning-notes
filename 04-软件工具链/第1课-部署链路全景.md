## 一、核心一句话

**部署 = 五步流水线：训练模型 → 导出 ONNX → 转换成 .rknn（同时量化）→ 推到板子 → 板端运行时加载推理。**
其中".rknn"不是一个通用格式，而是**针对指定芯片编译出来的任务包**（权重 + 量化参数 + 任务描述）——这正是阶段三说的"任务列表"的来源。

---

## 二、链路全景图

```
[PC / 服务器]                                  [开发板]
PyTorch / TensorFlow（训练，得到浮点模型）
      │  export
      ▼
   ONNX（通用中间格式，"模型界的 ELF"）
      │  RKNN-Toolkit2（Python，PC 端）
      │   ├─ config：指定目标芯片 target_platform、均值方差
      │   ├─ load_onnx
      │   ├─ build：量化（吃校准数据集）→ 生成任务描述
      │   └─ export_rknn → yolo.rknn ──── adb/scp ────→ 板子
      │                                                        │
      ├─（可选）PC 仿真推理 inference() ← 不碰板子先验证正确性    ▼
      └─（可选）连板真机调试 target='rk3588'          librknnrt.so（C）或
        （走 adb + 板端 rknn_server 代理）            rknn-toolkit-lite2（Python）
                                                     加载 .rknn → NPU 推理
```

### 为什么要 ONNX 这一步

训练框架太多（PyTorch/TF/JAX…），芯片厂商不想每家都适配。ONNX 是大家公认的中间表示——**训练框架解耦**。类比 IC 世界：RTL 是各家写的，综合工具吃的是统一网表。

### 为什么 .rknn 绑定芯片

`rknn.config(target_platform='rk3588')` 编译时，工具链按**这颗芯片的**算子清单、数据排布（NC1HWC2）、量化方案（3566 没有 FP16 可留）生成任务描述。**RK3588 编译的 .rknn 不能跑在 RK3568 上**，换芯片要回 PC 重新转换（好在流程一模一样，改一个字符串）。

## 三、核心脚本走读（model zoo 通用套路）

RKNN-Toolkit2 装 PC 上（仅 Linux x86_64 / ARM64 的 wheel，Windows 官方走 WSL）。转换一个 YOLOv5s 只需这几行（摘自官方 rknn_model_zoo 的 convert.py 风格）：

```python
from rknn.api import RKNN

rknn = RKNN(verbose=True)

# ① 配置：目标芯片 + 输入归一化参数（每通道均值/方差，来自训练时的预处理）
rknn.config(mean_values=[[123.675, 116.28, 103.53]],
            std_values=[[58.395, 57.12, 57.375]],
            target_platform='rk3588')          # ← 换芯片只改这里

# ② 读入 ONNX
rknn.load_onnx('yolov5s.onnx')

# ③ 构建：量化（PTQ）。dataset 是校准图片路径列表（~100-300 张代表性图片）
rknn.build(do_quantization=True, dataset='./dataset.txt')

# ④ 导出
rknn.export_rknn('yolov5s_rk3588.rknn')

# ⑤（可选）PC 仿真验证：不传 target 就在本机模拟器上跑
rknn.init_runtime()                # 想连真机则 target='rk3588'
outputs = rknn.inference(inputs=[img])
```

五个调用对上五个概念：**config=芯片差异，load=读模型，build=量化+编译，export=打包，inference=仿真或连板**。第 1 课学的"校准定 scale"，就发生在 `build()` 内部——工具链跑浮点模型、统计每层范围、定每层量化参数。

## 四、量化相关工具（阶段二"救援阶梯"的实操入口）

| 工具/参数 | 干什么 | 什么时候用 |
|---|---|---|
| `build(do_quantization=True, dataset=…)` | 训练后量化 PTQ | 默认路线 |
| `accuracy_analysis()` | 逐层对比量化/浮点输出（余弦距离），**定位哪层掉精度** | 精度不对先跑它 |
| 混合量化 step1/step2 | 手工指定敏感层保 FP16 | 分析出某几层是元凶后 |
| 自动混合精度（v2.3.2+） | 工具自动决定哪些层留高精度 | 懒人版 step1/2 |
| `quantized_dtype='w4a16'`（group 32/64/128） | 权重 4bit + 激活 FP16（02 第 1 课 W4 理论的实操） | **仅 RK3576/RV1126B**（v2.3.0+）——RK3576 主人专属 |
| `do_quantization=False` | 纯 FP16 模型（仅 3576/3588） | 追求精度不在意速度 |

经验顺序：**换校准集 → accuracy_analysis → 混合量化 → 考虑换模型**。

## 五、工具链家族全员表（别混淆）

| 名字 | 跑在哪 | 语言 | 职责 |
|---|---|---|---|
| RKNN-Toolkit2 | PC | Python | 转换/量化/仿真/性能评估（本课主角） |
| librknnrt.so | 板端 | C/C++ | 运行时：加载 .rknn、驱动 NPU（下节课主角） |
| rknn-toolkit-lite2 | 板端 | Python | 运行时的 Python 皮（现并入 rknn-toolkit2 仓库，pip 可装） |
| rknn_server | 板端 | 后台服务 | 代理 PC 经 adb/USB 发来的请求（联调真机用） |
| librga | 板端 | C | 图像预处理硬件（缩放/色转）的库 |
| rknn-llm | PC+板 | Python/C | **LLM 专用**另一条线（阶段六联动） |
| rknn3-toolkit | PC | Python | 下一代芯片（RK1820 等）的新工具链，现阶段了解即可 |

老版 RKNN-Toolkit（v1，RK1808/RK3399Pro 时代）与 v2 **互不兼容**——看到老教程先确认它讲的是 v1 还是 v2，这是搜教程最大的坑。

### 官方模型库：rknn_model_zoo

GitHub `airockchip/rknn_model_zoo`：分类（MobileNet/ResNet）、检测（YOLOv5~v11 全家桶）、分割、姿态、人脸、车牌、OCR（PPOCR）、语音（Whisper）…每个例子自带转换脚本+板端 C demo+FPS 基准表，`build-linux.sh` 一键编译。**第一个实践任务就从这里抄**，不要自己从零写。

## 七、IC 验证视角

工具链 = NPU 的"编译器"，验证工程师的类比：

- `build()` 生成的任务描述 ≈ 汇编器输出 → **金种子来源**：拿真实 .rknn 的任务流当 DV 激励，比随机激励有效一个量级
- accuracy_analysis 的"逐层余弦距离"思路 = **验证环境的逐级 scoreborad**：错误要定位到层/指令，不是只看最终输出
- 工具链 bug 会伪装成硬件 bug（量化错了 vs NPU 算错）→ 调试第一问："PC 仿真和板端真机结果一致吗？"——**仿真对、真机错 → 嫌疑在驱动/硬件；仿真也错 → 嫌疑在模型/量化**
