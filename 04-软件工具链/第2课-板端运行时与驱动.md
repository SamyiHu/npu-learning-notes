## 一、核心一句话

**应用调 NPU 的样子 = 打开设备、建上下文、查模型接口规格、填输入、跑、取输出、销毁——七步，全程不碰寄存器。**
细节被两层包掉：`librknnrt.so`（用户态运行时，干重活）和内核 rknpu 驱动（上电/映射/递交）。

## 二、C API 七步流（板端应用骨架）

```c
rknn_context ctx;

// ① 初始化：读入 .rknn 模型（RK3588/RK3576 可在此传 core_mask 绑核）
rknn_init(&ctx, model_data, model_size, 0, nullptr);

// ②③ 查接口：模型要什么输入、给什么输出（尺寸/格式/量化参数都从模型里问出来）
rknn_query(ctx, RKNN_QUERY_IN_OUT_NUM,     &io_num, …);
rknn_query(ctx, RKNN_QUERY_INPUT_ATTR,     &input_attr, …);   // 如 1×640×640×3, INT8
rknn_query(ctx, RKNN_QUERY_OUTPUT_ATTR,    &output_attr, …);  // 含量化 scale/zero_point

// ④ 填输入：把（预处理后的）图像包进 rknn_input 结构
rknn_inputs_set(ctx, 1, &input);

// ⑤ 跑
rknn_run(ctx, nullptr);

// ⑥ 取输出：拿到的是 INT8 张量 + 量化参数，CPU 侧反量化成浮点
rknn_outputs_get(ctx, 1, &output, …);
// …后处理（解码框、NMS 都在 CPU）…
rknn_outputs_release(ctx, 1, &output);   // 用完放回

// ⑦ 销毁
rknn_destroy(&ctx);
```

要点：

- 模型的输入输出规格是 **`rknn_query` 问出来的，不是写死的**——同一个应用换模型不用改代码结构
- 输出是 **INT8+scale**（呼应阶段二：整数算完，比例在这乘回），反量化和 NMS 在 CPU 上做
- 绑核（RK3588 三核 / RK3576 双核）：`rknn_set_core_mask(ctx, RKNN_NPU_CORE_0)`，多个模型各绑一核并行就是多次 init 多次 set（3588 三个、3576 两个）

### Python 等价物

板端 `rknn-toolkit-lite2`（pip 装）把上面七步包成 `RKNNLite()` 的几行调用，验证/原型用；产品走 C（省内存、快）。

## 三、预处理：RGA 硬件出场

摄像头/图片很少正好是模型的输入规格（如 1920×1080 NV12 → 640×640 RGB）。谁来变？——**RGA**（Rockchip 的 2D 图像加速器；型号随芯片不同：**RK3576 内是两枚 RGA2-Pro**，RK3588 内 RGA3 与 RGA2-Enhance 共存，RK3566/3568 是单枚 RGA2-Enhance——查型号认 airockchip/librga 开发者指南的芯片对照表，别信搜索引擎）：

```
CPU+OpenCV 做：占满一个 CPU 核，还多几趟内存拷贝
RGA 做：       硬件一拍完成 resize/裁剪/色转，CPU 完全闲着
```

librga（im2d API）典型用法：`importbuffer_fd()` 把 dma-buf 缓冲导入 RGA → 设置源/目标矩形和格式 → `improcess()` 一步完成。model zoo 的 C demo 里 `convert_image_rga()` 就是现成范例。

### 零拷贝串联（把 03 第 2 课的"别重复搬"落地）

```
摄像头(V4L2) ──dma-buf──→ RGA 缩放/色转 ──dma-buf──→ NPU
                （全程只传"缓冲句柄 fd"，数据不动窝）
```

RKNN 对应接口：`rknn_create_mem_from_fd()` + `rknn_set_io_mem()`（头文件里明确标注 "new api for zero copy"），跨硬件同步还有 `fence_fd`。入门先不用管，知道**为什么存在**即可：省 DDR 带宽（阶段三的账）。

## 四、驱动层：应用脚下是什么

```
你的程序 (app)
   │ 链接
librknnrt.so   ← 用户态运行时：解析 .rknn、生成任务列表、ioctl 递交
   │ ioctl / mmap
内核 rknpu 驱动 (drivers/rknpu/, DRM 框架)
   │ 寄存器/中断/总线
NPU 硬件（3 核 + IOMMU）
```

- 驱动暴露两类设备节点：DRM render node（`/dev/dri/renderD128` 风格）+ misc 设备 `/dev/rknpu`
- NPU 在设备树里描述（RK3588：`npu@fdab0000`，三段寄存器、三个中断、独立电源域；RK3576：`npu@27700000`，双核双中断同款思路）——设备树细节在 07 补课线第 3 课
- 主线内核另有社区的 rocket 驱动（accel 框架），属开源替代路线，生产生态仍用 vendor 驱动

### 板端排查三件套（背下来）

```bash
cat /proc/rknpu/version                 # 驱动版本（联调前先看）
cat /sys/kernel/debug/rknpu/load        # NPU 占用率（0% → 模型没跑上 NPU，回退 CPU 了！）
dmesg | grep -i rknpu                   # 驱动报错（版本不匹配/固件缺失在这哭）
```

**版本配套**是第一大坑：板端 `librknnrt.so` 版本要和 PC 端 Toolkit2 版本配套，驱动太老要升级固件/内核（如 RK3588S 上 core_mask 需驱动 ≥0.9.6）。报"驱动版本过低"就顺这条查。

## 六、IC 验证视角

- **运行时库 = 硬件的"参考模型使用者"**：DV 环境里对齐软件栈行为（任务递交顺序、缓冲布局）能提前暴露集成问题
- **ioctl 接口**是内核/硬件边界，fuzz 这个接口（非法 job、乱序递交、超时）是驱动验证的常规项
- **零拷贝/fence 的竞态**：多硬件单元共享缓冲，谁先写谁先读，验证组合空间大——和 SoC 级验证接轨
